## 1. 产品结论

启幕以 Agent、画布、插件、技能为四个核心。工作台是业务配置与扩展的组合入口：

**工作台 = 业务上下文 + 插件依赖 + 技能/配方选择 + 交互布局 + 输出投影。**

Agent 决定如何完成目标；技能提供方法；插件提供可调用的能力；画布让用户组织、修改和比较业务对象与结果。会话、权限、Task、资源、计费、持久运行构成共用支撑层，不是新的独立业务产品。

画布是核心交互能力，但不是所有调用的前置条件。批量素材同步、商品信息查询、文本分析等可以无画布执行；成果随后按需展示在画布中。

短剧、电商、设计营销应通过同一套组合机制扩展。确实需要新算法、复杂业务规则或特殊交互时，通过宿主 Adapter、受控远程服务或后续隔离运行时扩展，不能承诺任意应用在第一版完全零代码接入。

## 3. 值得吸收的产品能力

| 报告中的思路 | 在启幕中的归属 | 采用方式 |
| --- | --- | --- |
| 多入口共享 Agent | 会话外层与工作台组合 | 同一 Thread 可在首页和画布继续，执行轮次保持各自上下文快照 |
| 动态底部工具栏 | 宿主 Composer + 插件表单/启动配置 | 选择能力后显示所需素材、模型参数及报价，不复制多个 Composer |
| 选择技能后出现专属输入 | Skill 的可选启动绑定 + Operation Schema | 保留自然的“选技能开始做”体验，执行与参数校验归 Operation |
| 商品、角色、品牌成为长期资产 | 业务对象合同 + 现有资产/资源引用 | 使用稳定 ID/版本，支持选择、编辑、跨插件引用 |
| 创意、Hook、风格组合 | 版本化 Recipe/模板配置 | 保存结构化选择与合成结果，不只追加名称到 prompt |
| Agent/直接生成切换 | 两类调用入口 | 共享能力、参数、授权和结果；明确单操作可直接执行，不强制经过 LLM |
| 画布开关 | 输出展示策略 | 关闭时照常保存结果；开启时做受控投影，不触发再次生成 |
| Artifact 时间线 | ResultRef/Resource 的展示与引用索引 | 展示产物与来源，不再建第三套执行状态机 |

## 4. 必须修改后再吸收的建议

### 4.1 不把 Skill 扩成第二个执行引擎

旧报告建议 Skill 同时携带模型、计费、输入和工作流。用户体验值得采用，职责需要拆开：

- Skill：使用说明、示例、适用条件、方法及可选启动绑定。
- Operation：输入输出、真实效果、执行器与模型能力要求。
- Pipeline：确定步骤、持久等待、恢复和取消。
- Recipe：默认参数、推荐素材/风格、操作与技能组合。
- 宿主：模型解析、报价、审批、额度和执行权限。

纯 Markdown 技能继续有效，不强制每个技能绑定流程。技能的启动绑定可以引用一个 Operation 和表单视图；工具栏输入 Schema 从该 Operation 解析，不能在 Skill 再复制一份必填字段。技能提出模型偏好不等于强制选择任意模型，更不能声明最终价格。

### 4.2 不把工作台类型写死

旧提案的 `creative | short_drama | marketing | canvas` 可作为首批内置配置，但不能成为所有业务的固定枚举。建议分开三个概念：

| 概念 | 示例 | 含义 |
| --- | --- | --- |
| hostSurface | agent-home、canvas、editor | 宿主已实现的展示容器，首期可以是有限集合 |
| workbenchId | 官方短剧、某作者电商工作台的注册 ID | 可扩展的业务配置；服务端从已安装发布解析，不能接受任意字符串即授权 |
| contextRefs / outputBindings | 商品版本、项目、源画布、结果目标画布 | 本轮实际可访问对象与输出位置 |

工作台不拥有自己独立的 Agent Runtime。它声明推荐能力集合，实际工具范围仍由宿主权限和操作可用性决定。新工作台的路由优先使用通用入口按 ID 加载；独立友好路由可作为别名，不要求每个插件修改 router。

### 4.3 分开产物类型、展示目标和执行状态

旧 outputTarget 将 text/media/script 与 canvas/artifact 混在同一枚举中。前者是产物类型，后者是容器或概念，不宜互斥：一个视频既可在会话展示，也可绑定画布和编辑器。

保留 Operation 输出 Schema 表示产物；使用独立输出绑定表达显示在哪里。画布关闭仅影响新投影，不能撤销运行中已批准的必要画布操作。要求画布作为输入/执行上下文的操作，不会因为输出开关关闭就变成无画布操作。

旧 `idle → drafting → quoting → artifact_ready → canvas_committing` 可作界面阶段，不能替代 PluginRun/Task 状态。reconnecting 是连接状态；投影冲突是展示状态；两者都不能令已成功作业重新执行。

### 4.4 不按业务增加核心工具和 Task 类型

旧计划为营销、短剧分别增加大量工具和 remake 专属 Task，容易形成新的业务分支。业务操作优先注册成 `pluginId.operationId`，由统一 operation_invoke 调用；模型/HTTP 重作业通过已有 Task 与拟新增 plugin_operation 执行策略承载。

新增底层调度语义才考虑新 Task 类型；“又一个营销功能”本身不构成理由。前端 agentActions 仍只做纯规划，不把 JS 函数序列化上传 Go 后端执行。

### 4.5 外部产品限制不作为平台规则

报告中的商品图片数量、角色图片数量、视频时长、固定积分、实名二维码等是外部产品约束。启幕应按真实业务、模型、存储和权限确定限制，放在相关插件 Schema/策略中；宿主只施加统一资源上限。没有真实认证服务时，不创建一个看似有效的实名流程。

## 5. 可组合工作台的目标合同

以下是下一步合同设计要求，不是当前 v3 已支持字段。未来可以新增 `contributes.workbenches/recipes/objectTypes`，但须先确定完整 Schema、权限和渲染支持，并通过 hostApi/能力版本校验开放。未支持的宿主继续拒绝这些贡献，不能静默加载。

### 5.1 WorkbenchDefinition

至少声明：稳定 ID、名称、所需 hostSurface、插件依赖、推荐技能/配方、允许的操作入口、上下文 Schema、Composer 配置、命名视图布局、默认输出绑定策略。

这是可安装的配置，不是新执行器。它复用 PluginRelease 的版本、依赖和授权机制；运行开始固定 workbench releaseId。工作台停用阻止新启动，历史 Thread 与结果仍可读；升级不改变在途上下文。

Composer 控件使用宿主白名单。字段只绑定受 Schema 校验的输入，visibleWhen/disabledWhen 仅影响界面。推荐技能可以影响草稿但不能覆盖用户编辑；移除技能解除专属绑定，不删除用户上传资产。

### 5.2 Thread 与运行关系

Thread 是跨页面的用户会话容器，保存消息/轮次引用、工作台配置和上下文版本；不拥有第二套生成状态机。CloudAgentExecution 保存对话决策轮次，PluginRun 保存持久业务流程，Task 保存实际作业。

首页转画布时继续相同 Thread，创建新轮次或增加展示绑定，不复制既有 Task。一个 Thread 可以关联多个结果或画布，不在全局用一个可变 canvasId 覆盖历史轮次。

从短剧切到电商时，显式切换工作台上下文。默认展示相容资产并保留不相容草稿，不自动把商品当角色或把整段敏感历史发送给新增连接。已有 Run 的权限、输入和预算不随界面切换而变化。

### 5.3 Recipe 的组合规则

Recipe 表示创意、Hook、风格等可复用配置，可以引用 Skill、Operation/Pipeline、参数默认值与示例资产。它不是额外的 SkillRun，也不直接掌握凭证。

确定性组合顺序：宿主硬性约束与操作合同先裁定合法集合；工作台/配方提供默认建议；用户显式选择在合法集合内覆盖建议。多个配方的硬性要求冲突时显示冲突，不采用“最后一个覆盖”的隐式行为。

比如风格建议横屏，而用户选择竖屏，只在模型允许时接受；两个配方分别要求互斥的控制输入时拒绝组合。最终规范参数、引用版本和摘要进入运行快照并用于重新报价。

### 5.4 业务对象与跨插件复用

先建立统一引用：objectType、objectId、version、schemaVersion、owner/scope 及必要资源引用。商品、角色和品牌可以通过现有 Asset/AssetVersion 承载适合的版本化内容；复杂业务约束允许独立领域模型通过适配器暴露同一引用合同。

不直接把 PayloadJSON 当作已具备动态类型平台的证明。开放自定义 objectTypes 前需补 Schema 校验、可查询字段索引、引用删除保护、归属、迁移和配额；不开放任意 SQL 或任意字段索引。

公共对象 Schema 由平台维护语义；作者专有对象在插件命名空间内登记。两个插件都把字段命名为 product，不代表兼容。操作声明接受的对象/结果 Schema 和版本，必要转换通过显式操作处理，不让 Agent 猜字段后静默传入。

Artifact 可以作为业务结果的友好展示名称；其底层优先索引现有 ResultRef/Resource 或既有 Task 结果，不复制媒体、账务或批准事实。长期业务对象可引用多个产物版本，但与“一次生成输出”保持独立身份。

## 6. 与现有 v3 的实施顺序整合

插件 v3 M0–M7 继续作为执行底座主线，工作台补充采用独立 W 编号，不混淆两份旧里程碑编号。

| 补充阶段 | 接入位置 | 交付与关口 |
| --- | --- | --- |
| W0 合同对齐 | 插件 M0，并入 M2 非画布设计 | 明确 hostSurface/workbenchId、输入引用、输出绑定；明确 Thread 仅关联既有执行对象 |
| W1 单一工作台纵向样例 | 插件 M2–M5 | 同一个素材检查操作可由 Agent、表单按钮执行；结果在会话显示并可投影画布；两入口共用权限与调用合同 |
| W2 工作台配置和 Recipe | M5 后，与 M7 通用性验收配合 | 两个不同工作台用同一 Shell/Composer；配方冲突可解释；新增配置不改 Agent 主循环 |
| W3 业务对象扩展 | W2，先选一个真实对象族 | 商品或品牌的版本、归属、查询、引用与迁移验收；验证两个插件共享同一对象 |
| W4 应用生态开放 | W2/W3 稳定后 | 对作者开放受控 workbenches/recipes/objectTypes 合同和样例，后续再接审核/签名/隔离运行时 |

无需等全部工作台能力完成才实施一键出海；该应用可以先使用 v3 标准表单/蓝图。它同时检验复杂长流程，另选一个商品/品牌相关插件验证非视频通用性。不得把 W3 动态业务对象能力提前写成 v3 第一版已经具备。

旧首页方案把 Plugin Bridge 放在营销、短剧页面之后；按现在的生态目标，应前移统一操作入口，避免先完成两套硬编码页面再插件化。外层 Thread 和可选画布上下文与 v3 M2 合并设计，不重复实现两个通用 Run API。

## 7. 补充验收

- 增加第三个工作台不修改 Agent 调度与 Task 主循环；若依赖宿主未支持原语，安装时明确报缺失能力。
- 首页与画布继续同一 Thread，不重复生成/扣费；切换工作台不改变在途 Run 的输入与权限。
- 同一操作可从技能入口、按钮和流程执行，结果 Schema 与授权一致。
- 选择技能可带出输入槽；移除后保留用户草稿与上传资源，不覆盖用户已选模型参数。
- 直接生成可跳过 Agent 推理，但不能跳过 Schema、报价、批准和归属校验。
- 关闭画布后仍保存结果，之后加入画布不重跑模型；需要源画布的操作仍检查上下文。
- 同一商品/品牌版本可被不同插件读取，跨用户访问拒绝；被运行引用的版本不可误删。
- 组合两个互斥 Recipe 时提示冲突，最终参数与报价可追溯。
- 单纯换入口名称、配色或侧栏不算新工作台扩展验收；必须验证不同业务对象和操作组合。

本次是设计审查与整合，未实现上述合同、界面、数据库和执行能力。小云雀的交互结果是借鉴来源，最终实现仍以 qimu 的代码、资源与真实服务验证为准。
